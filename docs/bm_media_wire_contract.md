## 1. One media group on the wire

```text
<START IMG> ...          one message, <= 285 B
<I0>...  <I1>...  ...    `length` chunk messages
<I0>..<Ik>               video only: the KEYFRAME chunks again (section 5)
<END IMG> ...            one message, <= 295 B
```

Every message is one ASCII line ending in `\n`, sent on `spotter/transmit-data`
at the unit's configured pacing. **A JPEG/HEIC group is byte-identical to
today.** Nothing in this contract changes the still path.

## 2. `fmt` registry — media type is a property of the group

| START `fmt` | Media type | Payload | Filename ext |
|---|---|---|---|
| absent | image | HEIC (pre-Sprint08 units) | `.heic` |
| `pjpg` | image | progressive JPEG | `.jpg` |
| `heic` | image | HEIC | `.heic` |
| `h264` | **video** | raw Annex-B H.264 (section 6) | `.h264` |

Any other value: the backend treats the group as an image (today's behaviour)
and flags it. New values are added here first.

## 3. START keys

Order is fixed: `filename`, `timestamp`, `length` use `key: value`; everything
after `length` uses `key=value`.

| Key | Video | Example | Dropped for budget? | Meaning |
|---|---|---|---|---|
| `filename` | required | `2026-09-20T06-10-00Z_video_5s.h264` | never | `<capture UTC>_video_<N>s.h264` |
| `timestamp` | required | `2026-09-20T06:10:04Z` | never | send time, UTC |
| `length` | required | `126` | never | planned UNIQUE chunks (the keyframe repeat is not counted) |
| `fmt` | required | `h264` | never | section 2 |
| `fps` | required | `10` | never | playback rate — raw H.264 carries no timestamps |
| `dur` | required | `5.0` | never | clip seconds, one decimal |
| `res` | required | `480x270` | never | OUTPUT px: the encoded WxH of the clip that was sent. Says nothing about field of view |
| `crop` | required | `1600x900+1504+846` | never | FIELD OF VIEW: the sensor rectangle the clip shows, `WxH+X+Y` in NATIVE px (4608x2592 IMX708 frame = `video_geometry.crop_native_xywh`; full sensor = `4608x2592+0+0`). `na` = no camera (stored reference clip). No commas on the wire |
| `br` | one of `br`/`crf` | `40` | never | rate control = target bitrate, kbps. The product knob (section 6a) |
| `crf` | one of `br`/`crf` | `40` | never | rate control = x264 constant quality (lower = better). NOT `q`: `q` is JPEG quality on the opposite scale |
| `cmp` | required | `1` | never | 1 = complete send planned, 0 = bounded |
| `tz` `sha` `hn` + storage keys | optional | `hn=bmcam004` | yes, still builder's order | unchanged from stills |

Not sent for video: `q`, `att`, `rk`, `ws`, `we` (still-only).

Key-naming rules (forced by the parser):

1. **New keys go after `length`.** The fast-path START regex is positional
   (L76-81); the fallback takes the FIRST `chunks|length|len|buffer(s)` match
   (L88-91).
2. **No key may contain `len`, `chunks`, or `buffer`** — that regex has no word
   boundary. The tool and the test enforce this.
3. Keys are `[A-Za-z][A-Za-z0-9_]*`, values contain no space, comma, `;`, `>`
   (L100-102). `_clean_value` guarantees it on the device.
4. Unknown keys are parse-safe: captured into `start_header_fields`, ignored.
   **Measured:** today's staging parser reads every video key correctly,
   including `crop=1600x900+1504+846` and `br=40`.
5. Exactly one of `br` / `crf` is present: it names the rate control that
   produced the payload. The achieved size is never a key — it is `length`.

## 4. END keys

`<END IMG> filename: F, fmt: h264, uart_duration_sec: 129.0, sent_buffers: 126, cpu_temp_c: 41.2`

- Video END = the production END plus one core field `fmt`, right after
  `filename`. Still END is unchanged (no `fmt`).
- **END spells it `fmt: h264`, START spells it `fmt=h264`.** DECISION.md's
  example showed `fmt=` in END; the production END builder renders every field
  as `key: value`, and the parser accepts `=` or `:` for any key (L100-102) and
  normalises both to `fmt`. **Measured:** staging reads `end.fmt == "h264"` from
  the `: ` form. Using it means zero change to the END builder.
- `sent_buffers` = UNIQUE chunks actually sent. The keyframe repeat is not
  counted, so `sent_buffers == length` still means "everything went out".

## 5. Chunks

- **Legacy `<I{n}>` form only**, `n` = 0-based decimal index. The Sprint10
  `<I{gid}.{n}>` form is not understood by the backend (chunks silently
  dropped); `media_gid` stays disabled for video.
  **Rev 5:** superseded by the keyed form `<I{key}.{n}>` (section 14); the
  3-char `media_gid` form stays unsupported and is rejected.
- 384 base64 chars = 288 raw bytes per chunk (`bm_serial.image_buffer_size`);
  the last chunk is shorter and carries the padding. Every full chunk is a
  whole number of base64 quanta, so each decodes independently and a lost
  message costs exactly its own 288 bytes.
- Chunks carry no media type (D-S22-2): a chunk belongs to the open group for
  its node until END + all chunks, the next START, or a 600 s gap (L369).
- **Keyframe repeat (video only, rev 3):** after the last chunk and before END,
  chunks `0..k` are sent a second time, in order, byte-identical, where `k` is
  the last chunk that holds any byte of SPS, PPS or the IDR frame (the golden
  clip: keyframe ends at byte 2,236 -> chunks 0-7, 8 messages). The device caps
  the repeat at `video_tx.keyframe_repeat_max` (default 30).
  - Why the whole keyframe: every other frame is decoded from it. Lose chunk 0
    and nothing decodes; lose ANY keyframe chunk and the whole clip smears.
  - Why it is needed: **the camera cannot see a loss.** Measured 2026-09-21 on
    SPOT-33507C (fw v2.16.6): the Spotter logged `Queue MS_Q_CELLULAR_ONLY is
    full` for 16 s, 31-47 s after a 5-minute boundary, while its own scheduled
    transmission held the 2-slot queue, and silently rejected chunks 1-9 and
    11-17 of a clip. The Pi got no error. The repeat lands ~2 minutes later,
    outside that window.
  - The backend already dedupes by index keeping the longest payload
    (L615-617), so the repeat needs NO backend change. **Measured:** vectors
    `chunk0_lost` and `keyframe_lost` reassemble byte-exact.
  - `length` and `sent_buffers` still count UNIQUE chunks only.
- Cost: `k+1` extra paced messages per clip (8 on the golden clip; 15-30 typical).

## 6. Video payload

Raw Annex-B H.264, one keyframe (first frame), `yuv420p`, x264's
`user_data_unregistered` SEI (NAL type 6, payload type 5, ~690 B = 2 messages
of version string) removed. Everything else is exactly as encoded.

**Measured:** the strip is byte-identical to
`ffmpeg -c copy -bsf:v filter_units=remove_types=6` on the golden clip, so the
device can do it with one ffmpeg flag (no Python NAL parser on the Pi).

Why raw and not mp4: a tail-cut raw stream plays up to the cut; an mp4 with
`moov` at the end yields nothing (ladder step 2).

## 6a. `res` vs `crop` vs rate control — three independent customer settings

| Setting | Question it answers | Wire key | Config today (`video:` island) |
|---|---|---|---|
| crop | WHAT part of the scene? | `crop` | `crop_native_xywh` / preset (Sprint17, no-upscale rule) |
| res | HOW MANY pixels for that view? | `res` | output WxH |
| duration | how long? | `dur` | new in Phase 2 |
| rate control | how many BYTES (= messages)? | `br` or `crf` | new in Phase 2 |

On this link bytes are messages, so the budget maths is direct:
`br_kbps = usable_msgs x 288 x 8 / dur_s / 1000` (88 msgs, 5 s -> 40.5 kbps).
That lets the device reuse the progressive-JPEG time-budget idea
(`budget.max_messages_now()`) with no trial encodes. `crf` stays legal on the
wire for bench work. Which x264 mode hits a byte target accurately on a 5 s
clip (1-pass ABR / 2-pass / CRF+VBV cap) is NOT measured yet — Phase 2's first
bite re-runs the ladder by byte budget.

## 7. Partial clips

| What arrived | Backend result |
|---|---|
| all chunks + END | `is_complete=True`; store original, make display variant |
| all chunks, END lost | complete once the group closes (next START / 600 s gap) |
| tail cut (prefix only) | `is_complete=False`; transcode what decodes; record playable seconds. Golden: 84/126 chunks → 33/50 frames = 3.3 s |
| one mid chunk lost | `is_complete=False`; all frames decode with local damage. Golden: 125/126 → 50/50 frames |
| chunk 0 / keyframe chunks lost, repeat arrives | complete, byte-exact |
| a keyframe chunk AND its repeat lost | nothing decodable; keep the raw bytes, no display variant, flagged |
| START lost | group discarded — same as JPEG today. Not fixed this sprint |

Gaps are SKIPPED, never zero-filled: the backend joins the base64 of the chunks
that arrived in index order and decodes once (L303-304); the decoder resyncs on
the next start code.

## 8. Agreement rule (D-S22-4)

Four witnesses say what a group is: START `fmt`, END `fmt`, filename
extension, and the sniffed bytes (Annex-B = payload starts `00 00 00 01` or
`00 00 01`, first NAL type 7). The handler is chosen by **START `fmt`**.
Any witness that is present and disagrees sets a flag on the media row —
**flagged, never silently resolved**. A missing witness (END lost) is not a
disagreement. Golden vector `fmt_disagree`: START `h264`, END `pjpg`, bytes
H.264 → stored as video, flagged.

## 11. Q2 — who sends on the device, and what triggers it?

Product direction (Nick, 2026-09-20): the primary mechanism is **"record a
clip from config, then send it"** — commanded over Bristlemouth, or run as the
routine on wake/boot. "Send a clip that is already on the card" is secondary.

One pipeline, pluggable source — the same shape as the still `trg` table
(`action` + `src`):

```text
source ──> fit to config (crop, res, dur, byte budget) ──> START/chunks/END
  cam : record `dur` s now, at the configured crop/res     (product path)
  ref : stored reference clip, camera bypassed             (pipeline proof)
  ring: newest finished clip on the card                   (continuous-record units)
```

| Proposed | Meaning | Mirrors still |
|---|---|---|
| `trg 5` | record a video per config + send | `trg 2` capture + send |
| `trg 6` | send the stored reference video (camera bypassed) | `trg 3/4` |
| `trg 7` | send the newest recorded clip | — |

Who issues it: a person or the dashboard, through the existing command
downlink (Sofar API -> Spotter -> BM bus -> camera, Sprint10-13). It is
persisted as `pending_trigger` and fires at the unit's next opportunity.
A scheduled/boot routine runs the same `cam` pipeline with no command at all.

UART ownership (confirmed from code) decides WHEN it fires:

| Unit runtime | Who owns `/dev/ttyAMA0` | Trigger fires |
|---|---|---|
| wake -> cycle -> halt (stills doctrine) | the cycle process | next boot, like `trg 2`. No contention: nothing else is recording |
| continuous recorder (`capture_mode: video`) | `run_video_mode`'s in-process daemon, for the whole session (D-S15-7) | next clip boundary, inside that process; recording pauses for encode + send |

The `ref` source is the end-to-end proof: the device sends the committed
`payload.h264` verbatim, so the backend's sha256 must equal the golden
`5fd3ce55...` — known start state, known end state, every loss visible
(testsrc2 burns a frame counter into the picture).

Not built; `TABLES_VERSION` 7 -> 8; gated by `video_tx.enabled` (default false).

## 14. Rev 5 — keyed media (self-healing)

Why: a lost START loses the whole group, and a chunk cannot be re-sent later
unless it names the media it belongs to (Sprint25 `RESULTS.md`). Design:
`nereus-vision-dev/backend/docs/SPEC_resend_heal.md` v3 §2 (wire) and §3 M0;
device half `sprints/Sprint25_transmit_timing_resend/RESEND_DEVICE.md` v3 §2.

### 14.1 Media key

- 6 lowercase base-36 chars (`[0-9a-z]{6}`), zero-padded = whole seconds
  since `2026-01-01T00:00:00Z`. Example: 2026-09-20T06:10:00Z = 22,659,000 s
  → `0dhnso`. Range: 36^6 s ≈ 69 years.
- Taken **only from the Spotter UTC read of that wake**. No Spotter time this
  wake → the device sends the rev 3 legacy form (no key anywhere).
- Monotonic per device: the device persists the last key and never sends a
  key ≤ it (stale clock) → legacy form + a log line.
- Value < 0 or ≥ 36^6 → legacy form.
- A key is per media group; it is not a device id. The backend keys on
  `(device_id, key)`.

### 14.2 Placement

| Message | Rev 3 | Rev 5 |
|---|---|---|
| START | `... length: N, fmt=..., ...` | `... length: N, key=<key>, fmt=..., ...` — `key` is a **core key, immediately after `length`, never dropped by the budget** |
| chunk | `<I{n}>{base64}\n` | `<I{key}.{n}>{base64}\n` |
| keyframe repeat | `<I{n}>` | `<I{key}.{n}>`, same rule as section 5 |
| END | unchanged | **unchanged** (byte-identical to rev 3) |

- `key` obeys the section 3 naming rules (no `len`/`chunks`/`buffer`, value
  has no space, comma, `;`, `>`).
- Chunk size: 384 base64 chars as before. `<I` + 6 + `.` + up to 3 index
  digits + `>` + 384 + `\n` = **398 B** worst case. The Spotter accepts
  ≤ 1000 B per message and the fast path drains ≤ ~430 B (Sprint09 DEV_LOG
  :146-168): no payload shrink.
- Backend chunk regex: `<I([0-9a-z]{6})\.(\d+)>`. Anything else of the form
  `<I{x}.{n}>` — in particular the Sprint10 3-char `media_gid` — is
  **rejected** (not counted, not spliced).

### 14.3 Backend rules

- **M0 — lossless fallback (ships first, stays forever).** A keyed chunk is
  parsed as `<I{n}>` under the section 5 open-group rule; the key is ignored
  for grouping. A rev 5 unit against an M0 backend degrades to rev 3
  behaviour, never to silent loss. M0 is also the OFF state of the backend's
  keyed-grouping flag (rollback path).
- **Keyed grouping (later, behind a flag; spec §2/§3 M3).** Per-node per-key
  state plus one legacy slot; a keyed message belongs to `(device_id, key)`
  whenever it arrives, so chunks may arrive after END or in a later window
  (heals). Dedupe by `(device_id, key, n)`, longest payload wins. Same key with
  a different `filename`/`length`/`sha` → flagged `media_key_collision`, never
  merged.
- **A legacy `<I{n}>` after a keyed START on the same node is flagged, never
  spliced** into the keyed group.

### 14.4 Device rules

- Behind the YAML island `media_key.enabled`, **default OFF** until M0 is live
  on staging. OFF → every rev 3 golden wire stays byte-identical. ON → a
  separate rev 5 golden set.
- Same builder for images and video. `rc_media_id` (3-char gid) is retired.

### 14.5 Vectors

Backend (`nereus-vision-dev/backend/tests/fixtures/bm_media_keyed_m0/`, built
from the section 12 golden clip): `keyed_as_legacy_complete` (byte-exact,

partial), `three_char_gid_rejected` (0 chunks accepted). Rev 3 vectors
(`legacy_unchanged`) stay green unchanged. The full keyed-grouping list is in
the spec §8.
