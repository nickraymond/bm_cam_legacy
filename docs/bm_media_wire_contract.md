# BM media wire contract — images and short video over Spotter

**Status: DRAFT for Nick's sign-off (Sprint22 Phase 0 gate).** Key names are
hard to change once units are in the field; nothing downstream (backend,
device, cellular) starts until this is signed.

Decisions: `sprints/Sprint22_video_over_spotter/DECISION.md` (D-S22-1..6).
Golden vectors: `tests/vectors/bm_media_h264/` (generated by
`tools/bm_video_tx_loopback.py --golden`, pinned by
`tests/test_bm_media_golden_vectors.py`). This file is mirrored byte-identical
into `nereus-vision-dev` in Phase 1; this repo is the source of truth because
the device produces the wire.

Backend line references are `backend/app/services/bm_image_parser.py` on
`origin/staging` @ `516b813`.

## 1. One media group on the wire

```text
<START IMG> ...          one message, <= 285 B
<I0>...  <I1>...  ...    `length` chunk messages
<I0>...                  video only: chunk 0 repeated (section 5)
<END IMG> ...            one message, <= 295 B
```

Every message is one ASCII line ending in `\n`, sent on `spotter/transmit-data`
at the unit's configured pacing. **A JPEG/HEIC group is byte-identical to
today.** Nothing in this contract changes the still path.

## 2. `fmt` registry — media type is a property of the group

| START `fmt` | Media type | Payload | Filename ext |
|---|---|---|---|
| absent | image | HEIC (pre-Sprint08 units) | `.heic` |
| `pjpg` | image | progressive JPEG | `.jpg` |
| `heic` | image | HEIC | `.heic` |
| `h264` | **video** | raw Annex-B H.264 (section 6) | `.h264` |

Any other value: the backend treats the group as an image (today's behaviour)
and flags it. New values are added here first.

## 3. START keys

Order is fixed: `filename`, `timestamp`, `length` use `key: value`; everything
after `length` uses `key=value`.

| Key | Video | Example | Dropped for budget? | Meaning |
|---|---|---|---|---|
| `filename` | required | `2026-09-20T06-10-00Z_video_5s.h264` | never | `<capture UTC>_video_<N>s.h264` |
| `timestamp` | required | `2026-09-20T06:10:04Z` | never | send time, UTC |
| `length` | required | `126` | never | planned UNIQUE chunks (the repeat is not counted) |
| `fmt` | required | `h264` | never | section 2 |
| `fps` | required | `10` | never | playback rate — raw H.264 carries no timestamps |
| `dur` | required | `5.0` | never | clip seconds, one decimal |
| `res` | required | `480x270` | never | encoded WxH |
| `crf` | required | `40` | never | x264 CRF (lower = better). NOT `q`: `q` is JPEG quality on the opposite scale |
| `cmp` | required | `1` | never | 1 = complete send planned, 0 = bounded |
| `tz` `sha` `hn` + storage keys | optional | `hn=bmcam004` | yes, still builder's order | unchanged from stills |

Not sent for video: `q`, `att`, `rk`, `ws`, `we` (still-only).

Key-naming rules (forced by the parser):

1. **New keys go after `length`.** The fast-path START regex is positional
   (L76-81); the fallback takes the FIRST `chunks|length|len|buffer(s)` match
   (L88-91).
2. **No key may contain `len`, `chunks`, or `buffer`** — that regex has no word
   boundary. The tool and the test enforce this.
3. Keys are `[A-Za-z][A-Za-z0-9_]*`, values contain no space, comma, `;`, `>`
   (L100-102). `_clean_value` guarantees it on the device.
4. Unknown keys are parse-safe: captured into `start_header_fields`, ignored.
   **Measured:** today's staging parser reads all nine video keys correctly.

## 4. END keys

`<END IMG> filename: F, fmt: h264, uart_duration_sec: 129.0, sent_buffers: 126, cpu_temp_c: 41.2`

- Video END = the production END plus one core field `fmt`, right after
  `filename`. Still END is unchanged (no `fmt`).
- **END spells it `fmt: h264`, START spells it `fmt=h264`.** DECISION.md's
  example showed `fmt=` in END; the production END builder renders every field
  as `key: value`, and the parser accepts `=` or `:` for any key (L100-102) and
  normalises both to `fmt`. **Measured:** staging reads `end.fmt == "h264"` from
  the `: ` form. Using it means zero change to the END builder.
- `sent_buffers` = UNIQUE chunks actually sent. The chunk-0 repeat is not
  counted, so `sent_buffers == length` still means "everything went out".

## 5. Chunks

- **Legacy `<I{n}>` form only**, `n` = 0-based decimal index. The Sprint10
  `<I{gid}.{n}>` form is not understood by the backend (chunks silently
  dropped); `media_gid` stays disabled for video.
- 384 base64 chars = 288 raw bytes per chunk (`bm_serial.image_buffer_size`);
  the last chunk is shorter and carries the padding. Every full chunk is a
  whole number of base64 quanta, so each decodes independently and a lost
  message costs exactly its own 288 bytes.
- Chunks carry no media type (D-S22-2): a chunk belongs to the open group for
  its node until END + all chunks, the next START, or a 600 s gap (L369).
- **Chunk-0 repeat (video only):** after the last chunk and before END, `<I0>`
  is sent a second time, byte-identical. With the SEI stripped, chunk 0 holds
  SPS+PPS (byte 42 of 288 in the golden clip) — lose it and 0 frames decode.
  The backend already dedupes by index keeping the longest payload (L615-617),
  so the repeat needs no backend change. **Measured:** vector `chunk0_lost`
  reassembles byte-exact on today's staging parser.
- Cost: one extra paced message per clip.

## 6. Video payload

Raw Annex-B H.264, one keyframe (first frame), `yuv420p`, x264's
`user_data_unregistered` SEI (NAL type 6, payload type 5, ~690 B = 2 messages
of version string) removed. Everything else is exactly as encoded.

**Measured:** the strip is byte-identical to
`ffmpeg -c copy -bsf:v filter_units=remove_types=6` on the golden clip, so the
device can do it with one ffmpeg flag (no Python NAL parser on the Pi).

Why raw and not mp4: a tail-cut raw stream plays up to the cut; an mp4 with
`moov` at the end yields nothing (ladder step 2).

## 7. Partial clips

| What arrived | Backend result |
|---|---|
| all chunks + END | `is_complete=True`; store original, make display variant |
| all chunks, END lost | complete once the group closes (next START / 600 s gap) |
| tail cut (prefix only) | `is_complete=False`; transcode what decodes; record playable seconds. Golden: 84/126 chunks → 33/50 frames = 3.3 s |
| one mid chunk lost | `is_complete=False`; all frames decode with local damage. Golden: 125/126 → 50/50 frames |
| chunk 0 lost, repeat arrives | complete, byte-exact |
| chunk 0 AND repeat lost | nothing decodable; keep the raw bytes, no display variant, flagged |
| START lost | group discarded — same as JPEG today. Not fixed this sprint |

Gaps are SKIPPED, never zero-filled: the backend joins the base64 of the chunks
that arrived in index order and decodes once (L303-304); the decoder resyncs on
the next start code.

## 8. Agreement rule (D-S22-4)

Four witnesses say what a group is: START `fmt`, END `fmt`, filename
extension, and the sniffed bytes (Annex-B = payload starts `00 00 00 01` or
`00 00 01`, first NAL type 7). The handler is chosen by **START `fmt`**.
Any witness that is present and disagrees sets a flag on the media row —
**flagged, never silently resolved**. A missing witness (END lost) is not a
disagreement. Golden vector `fmt_disagree`: START `h264`, END `pjpg`, bytes
H.264 → stored as video, flagged.

## 9. What today's backend does with a video group (why backend lands first)

**Measured** by running the staging parser over the golden vectors:

| Behaviour | Today | Needed (Phase 1) |
|---|---|---|
| Reassembly, dedupe, `fmt`/`fps`/... key capture | correct, byte-exact on all 5 vectors | no change |
| Filename | rewritten `..._video_5s.h264` → `..._video_5s.jpg` (`ALLOWED_EXTS`, L13, L112-113) | allow `.h264` |
| `sniff_format` | `None` (L207-222) | Annex-B branch |
| Stored as | `image/jpeg`, `type=image`, complete; worker burns 3 failed jobs | `type=video`, `format=h264`, right Content-Type |

## 10. Q1 — is ffmpeg on the Render backend? **Not provably; use PyAV.**

- `origin/staging` has no `render.yaml`, no `Dockerfile`, no build script; docs
  say native Python runtime (`PYTHON_VERSION=3.13.5`, `requirements.txt`), 512 MB
  instances, ingest in the `nereus-sofar-ingest-staging` cron. `requirements.txt`
  has no ffmpeg/PyAV. The build command lives in the Render dashboard.
- A native runtime has no `apt`, so "add ffmpeg to the build" really means
  "move the service to Docker" — a deploy-model change, out of proportion.

| Option | Deploy change | Verdict |
|---|---|---|
| **PyAV (`av` wheel)** | one line in `requirements.txt` (~44 MB installed) | **recommended** |
| system `ffmpeg` via `subprocess` | unverifiable from the repo; Docker if absent | no |
| `opencv-python-headless` (already pinned) | none | decodes H.264, but its wheel has no H.264 encoder → cannot write a browser-playable mp4 |

**Measured** (PyAV 18.1.0 wheel, Python 3.13, Mac): bundles the h264 decoder
and the libx264 encoder; golden `complete` → mp4 50 frames / 5.0 s / 10 fps;
`tail_cut` → 33 frames / 3.3 s; `mid_lost` → 50 frames; poster JPEG from frame
0 via Pillow. The display variant is a **decode + re-encode**, not a `-c copy`
remux — that sidesteps the ladder's B-frame remux bug (dropped frame, scrambled
pts) and cleans up concealed damage. `fps` comes from START.

Not verified: the Linux wheel on Render itself, and peak RSS on the 512 MB
instance (expected small at 480x270). First Phase 1 step = add `av`, deploy,
transcode the golden clip on staging.

## 11. Q2 — who sends on the device, and what triggers it?

**Confirmed from code:** in video mode `rc_progressive_jpeg.py` dispatches to
`video_recorder.run_video_mode`, whose in-process command daemon owns
`/dev/ttyAMA0` for the whole session (D-S15-7). A second process cannot send.
The send must run inside that process, through its open BM serial.

Proposal (Phase 2, not built):

- **Where:** at the clip boundary in `run_video_mode`, after the existing
  `status flush -> daemon drain`. rpicam-vid is not running there, so no
  camera contention; the send reuses the `rc_transmit` loop, whose
  `pending_pump_fn` / `ack_drain_fn` keep commands flowing mid-burst.
- **Cost, stated plainly:** recording pauses for encode (5-23 s) + send
  (~130 s for 126 msgs at 1 msg/s). Acceptable for a commanded demo; a
  background sender is future work.
- **Trigger:** new one-shot `trg 5` = "send newest video clip (video mode)",
  `TABLES_VERSION` 7 → 8. Reuses the persisted `pending_trigger` /
  `consume_trigger()` machinery; consumed at the next clip boundary instead of
  the next boot. In stills mode `trg 5` is acked and ignored with a log line.
  Gated by `video_tx.enabled` (default false).

10 fps, CRF 40, x264 veryslow, one keyframe → **36,019 B = 126 chunks** after
